Well-Architected review

The six pillars of the AWS Well-Architected Framework, applied to Mabi as it runs now (after the incident fix, 2026-11-17). For each: what the framework asks, what Mabi does, and a verdict.

Operational excellence Good

Asks for: operations as code, small reversible changes, observability, learning from failure.

Mabi does: everything is in git (branding, content, config builder, compose file, start script, ops scripts, systemd timers, the CloudShell script that creates all monitoring). One script (start-mabi.sh) rebuilds the config from S3 and restarts the stack. Every request is logged with outcome, duration and version. A tested runbook exists, and the one incident led to a real change (auto-heal).

Weak spot: deployment is still a manual git pull in Session Manager; no CI/CD.

Security Adequate

Asks for: strong identity, least privilege, traceability, protection at every layer, data protection in transit and at rest.

Mabi does: root has MFA and is not used; daily work is an IAM user with MFA that switches into an admin role; the server has its own narrow role; the API key is a SecureString; CloudTrail logs all regions; no SSH; the server only accepts CloudFront; HTTPS for users; sign-up closed.

Gaps: no AWS WAF, so the login page and model quota have no rate limit; CloudFront to server is plain HTTP inside AWS; MongoDB has no password (it is reachable only from the Docker network); EBS encryption not confirmed.

Reliability Adequate

Asks for: automatic recovery, tested recovery, scaling, knowing when something fails.

Mabi does: 9 alarms to email; external health check every 5 minutes; auto-heal every minute; Docker restart: always; nightly backups to S3 with a 14-day lifecycle; restore tested (RTO 43 s); faults written up.

Gaps: a single instance in a single Availability Zone is a single point of failure; RPO is 24 hours; rebuilding a whole lost server is written down but not rehearsed; the free model tier rate-limits (HTTP 429) under steady use.

Performance efficiency Adequate

Asks for: right-sized resources, measuring performance, using managed services where they help.

Mabi does: t3.small (2 vCPU, 2 GiB) with 2 GB swap. On 2026-11-17 memory was about 52% and disk about 56% used, with CPU low. Logged answers took 1.1 to 7.7 seconds. CloudFront serves the static files from the edge. An alarm fires if average answer time exceeds 20 s.

Gap: the bottleneck is the external model's free-tier rate limit, not AWS; there is no load test, so the safe number of users is unknown.

Cost optimization Good

Asks for: pay only for what you use, measure spend, set guardrails.

Mabi does: AWS Free plan; one small instance; a $1 monthly budget that emails above $0.01; CloudWatch kept inside its free allowance on purpose (10 custom metrics, 9 alarms, 1 dashboard); log retention 14–30 days instead of "never expire"; S3 backups expire after 14 days; the model is free.

Gap: resources are not consistently tagged for cost allocation, and the server runs at night when nobody uses it.

Sustainability Adequate

Asks for: the smallest footprint that meets the need.

Mabi does: one small burstable instance, no idle extras, old backups and logs deleted automatically, caching static files at the edge.

Gap: it runs 24/7; a schedule that stops it overnight would cut its energy use by about a third.

Trade-off and the gap I would fix first

Optimised for: operational excellence and reliability-through-recovery (watch it, back it up, fix fast). Deliberately accepted as weaker: reliability-through-redundancy, because a second server or a managed database would leave the Free plan for a help desk with a handful of test users.

Gap ranked first: no AWS WAF in front of CloudFront (Security). The login page and the chat API are open to the whole internet with no rate limit. One script could guess passwords or burn the free Gemini quota, which would take Mabi down for everyone (we already saw 429 errors with one human tester). A WAF web ACL with the AWS managed common rules and a rate-based rule on /api/auth/login and /api/ask is a few clicks on the existing distribution, costs a few dollars a month, and protects security and availability at once. That beats the alternatives on value: Multi-AZ would cost far more, and the other security gaps (internal HTTP, Mongo without password) can only be reached by someone already inside the server.
